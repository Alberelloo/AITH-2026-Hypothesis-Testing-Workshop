# Встреча 3. Запуск и доверие к данным

## О чём встреча

Тест чекаута отработал 14 дней. Прежде чем считать эффект, проверяем, что платформа честно раздала группы и ничего не потеряла: сплит воспроизводится хешем, нет дублей и пользователей в обеих группах, доли групп совпадают с планом 80/20, события не теряются по-разному в группах. Сломанные данные дают «эффект», которого нет, и никакая статистика после этого не спасёт.

Кейс сквозной: `data/checkout_ab.csv` (подложены 250 дублей строк и 60 пользователей в обеих группах). Плюс пять выгрузок других тестов с SRM разной природы и тест виджета доставки с потерями телеметрии. Выход встречи — очищенные данные чекаута (вход встречи 6) и чек-лист запуска.

## Ключевые концепции

- **Сплитование** — `md5(соль:user_id) mod 10 000`, бакеты 0–1999 → B. Группа детерминирована и пересчитывается вне платформы: в логе чекаута ровно 60 строк, где группа ≠ хешу, — это и есть 60 «двойных» пользователей.
- **Как ломается сплит** — плохой хеш (CRC32 и Java `hashCode` при `% 2` дают φ = 1 между тестами с разными солями; `hashCode` при `% 100` — заметную связь), общая соль с прошлым тестом (совпадение групп 100%), отсутствие двойного посола в слоях (все `exp_1` в B, все `exp_2` в A). SRM ничего из этого не видит.
- **Множественные A/A по солям** — p-value равномерны и ~5% значимых при исправном сплите; с `hashCode` и остаточным эффектом прошлого теста — 26% ложных срабатываний и подозрительно ровные доли групп.
- **SRM** — χ² согласия против *заданного* сплита 80/20, порог p < 0.001. Чекаут после очистки: p = 0.49; по дням минимальный p = 0.032 — выше порога 0.001, который действует на каждую проверку без поправок. Мощность: 80% при потере 3.2% пользователей B за 14 дней.
- **Пять причин SRM** и их следы: баг назначения (дефицит в одном устройстве), ботфильтр после назначения (со всеми строками сплит честный), потери телеметрии (другая задержка событий, обрыв на окне пайплайна), редирект в одной ветке (дефицит в одном источнике), неверная дата старта / кэш (дефицит в первые дни).
- **Дубли и пользователи в обеих группах** — дубли схлопываем; «двойных» исключаем целиком (неизвестно, что они видели), затем снова SRM.
- **Телеметрия и триггеринг** — ITT честен, но разбавлен (×2.5 при доле триггера 40%); честный триггер определён одинаково в обеих группах и до воздействия; триггер по клиентскому событию с разной потерей смещён: при нулевом эффекте даёт +3.3 п.п. и 99% «значимых». Разбавленная оценка «эффект по триггеру × доля триггера» в 1.5 раза точнее прямой ITT.
- **Guardrail на старте** — первые 1–2 дня смотрим поломки (SRM, потери событий, ошибки оплаты) с порогом 0.001; рост ошибок оплаты с 2% до 4% виден за 2 дня почти наверняка.

## Вопросы для обсуждения

| Раздел | Вопрос |
| --- | --- |
| Сплитование | Зачем вычислять группу хешем, а не бросать монетку и записывать результат? |
| Как ломается сплит | Хеш сменили на CRC32, доли ровные, SRM молчит. Можно запускать тесты? |
| Качество выгрузки | Почему дубли схлопываем, а пользователей из обеих групп исключаем целиком? Когда это опасно? |
| SRM | В последний день p = 0.032. Это SRM? Что сказать владельцу продукта? |
| A/A по солям | Что покажут 200 A/A на Java hashCode с остаточным эффектом прошлого теста? Что, кроме доли значимых, стоит проверить? |
| Мощность SRM | SRM дал p < 0.001. Может, просто не повезло? |
| SRM-детектив | Какая причина SRM в каждом из пяти кейсов? Какой тест можно спасти? |
| SRM и эффект | В кейсе 4 эффекта нет по построению. Что покажет разница конверсий B − A «в лоб» и почему? Спасает ли разбивка по устройствам? |
| Триггеринг | Какой из трёх способов при нулевом эффекте «найдёт» эффект? А какой лучше всех найдёт настоящий? |
| Виджет доставки | Какой эффект писать в отчёт и почему оценка по клиентскому событию завышена? |
| Guardrail | Заметим ли за два дня рост ошибок оплаты с 2% до 3%? До 4%? Почему тест односторонний, а порог такой строгий? |
| Чек-лист | Все проверки, которые позволяет выгрузка, прошли. Значит, эффекту можно верить? |

## Артефакт

**Чек-лист запуска** — `launch_checklist.md`: 15 проверок в трёх разделах (до старта, первые 48 часов, перед анализом), у каждой — способ проверки, порог, действие при провале и пустые колонки «Факт» и «OK / что сделали». Один порог SRM на все проверки — p < 0.001 без поправок. В конце — строка решения и шпаргалка «пять причин SRM → где искать». Раздел ноутбука «Чек-лист запуска и данные для встречи 6» заполняет «Перед анализом» (и п. 4) для чекаута; все проверки, доступные по выгрузке, проходят (срезы п. 14 — только по дням; решение — «анализируем с оговоркой»), и раздел отдаёт во встречу 6 правило очистки и контрольные числа:

```python
def clean_checkout(raw: pd.DataFrame) -> pd.DataFrame:
    """Правило очистки встречи 3: схлопнуть полные дубли, исключить пользователей из обеих групп целиком."""
    dedup = raw.drop_duplicates()
    both = dedup.groupby('user_id')['group'].nunique().gt(1)
    return dedup[~dedup['user_id'].isin(both[both].index)].reset_index(drop=True)

CLEAN_CHECKOUT = {'rows_raw': 105330, 'period': ('2026-09-07', '2026-09-20'), 'n_users': 104960, 'n_a': 83878, 'n_b': 21082,
                  'srm_p': 0.487, 'dropped_duplicates': 250, 'dropped_users_both': 60}
```

Встреча 6 начинает с `checkout = clean_checkout(pd.read_csv('../data/checkout_ab.csv'))` и сверяет `n_a`, `n_b` с `CLEAN_CHECKOUT`.
