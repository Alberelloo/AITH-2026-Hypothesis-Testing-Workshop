# 5. Много метрик — одно решение

## О чём встреча

Тест посчитан, остановлен вовремя (встреча 4), и теперь на руках отчёт из десятков метрик, которые тянут в разные стороны. Это последний шаг жизненного цикла одного эксперимента: от отчёта к решению «внедряем / не внедряем / внедряем с условием». В базовом курсе мы проверяли одну гипотезу на одной метрике. Здесь их много: нужно проверить сплит, разложить метрики по ролям, вывести поправки на множественность из правила запуска и смотреть на сегменты без p-hacking.

## Из каких лекций курса

- «Множественное тестирование гипотез» — основа: FWER и FDR, поправки Бонферрони, Холма, Шидака, BH и BY, учёт поправок при дизайне, правило запуска по нескольким метрикам (Spotify).
- «Метрики и доверие к тесту» — роли метрик, закон Гудхарта, метрика-SRM, триггеринг, парадокс Симпсона, сегменты, чек-лист доверия к тесту. В «Дополнительно»: проверка метрик на корпусе, прокси и суррогаты, горизонт теста, потеря телеметрии, неполные воронки, закон Твайман.

## Ключевые идеи

- Отчёт читают по порядку: качество данных (SRM) → целевая метрика → guardrail → диагностические. При SRM результат не читают.
- Метрику-цель накручивают (закон Гудхарта), поэтому к ней до запуска добавляют guardrail-метрики и контрметрику.
- При m проверках без поправки хотя бы одно ложное открытие почти гарантировано. FWER ограничивает вероятность хотя бы одной ошибки, FDR — их долю. По умолчанию Холм для FWER и BH для FDR.
- Поправку выводят из правила запуска: «хотя бы одна метрика успеха» требует поправки α, «все guardrail» требуют поправки β, то есть больше выборки. Диагностические метрики решений не принимают.
- Поправки снижают мощность, поэтому их закладывают в размер выборки: выборку считают по Бонферрони, анализ проводят Холмом.
- Сегменты: заранее перечисленные, по признакам до назначения, с проверкой доли сегмента в группах. «Значим здесь, не значим там» не означает разницы эффектов, её проверяют через взаимодействие.
- Триггер повышает мощность, только если он определён одинаково в обеих группах. Если доля теста менялась, эффект считают внутри периодов (иначе получается парадокс Симпсона).
- Если guardrail не определился, это не «внедряем», а «внедряем с условием» или «продлеваем тест».

## Вопросы для обсуждения

1. Команда оптимизирует «среднее время в приложении». Тест нового экрана показал +9% к времени в приложении, а число заказов на пользователя не изменилось (p = 0.4). Запускаем?
2. Исследователь хочет объявить 14 человек из тысячи экстрасенсами, потому что они угадали 9 или 10 карт из 10. Что вы ему скажете и чего ждать от повторной проверки?
3. В отчёте одна целевая метрика, четыре guardrail и пятнадцать диагностических. Аналитик применяет процедуру Бенджамини–Хохберга ко всем двадцати p-value, а коллега возражает, что поправка нужна только целевой метрике. Кто прав?
4. В тесте 50/50 SRM нет. Метрика «среднее число заказов на активного пользователя» упала на 5%, а число заказов на пользователя не изменилось. Что проверить в первую очередь?
5. «На Android эффект значим (p = 0.03), на iOS нет (p = 0.30), запускаем только на Android». Что вы проверите до решения?
6. Заказы +1.8% (p = 0.004), время доставки +0.6 мин при интервале от −0.1 до +1.3 мин и границе +1 мин, три значимые диагностические метрики из пятнадцати. Продакт говорит: «внедряем, время доставки значимо не ухудшилось». Что вы ответите?
7. Скорость загрузки коррелирует с заказами на 0.9 на уровне пользователей. Можно ли принимать решения только по скорости как по прокси? (Дополнительно)
8. В акции со скидкой за первые три дня заказы выросли на 10%, p < 0.001. Продакт просит остановить тест и запускать на всех. Что вы ответите? (Дополнительно)
9. Клики по главной кнопке выросли на 28%, заказы не изменились, эффект по дням быстро убывает. Что вы скажете команде? (Дополнительно)

## Правило для команды

1. **Сначала сплит.** До чтения метрик проверяем SRM по пользователям (при менявшейся доле — внутри каждого периода) и знаменатели ключевых метрик. Есть SRM — результат не читаем, ищем причину.
2. **Роли и поправки — в дизайн-доке до запуска.** Метрики успеха (поправка α/S, анализ методом Холма), guardrail с границами non-inferiority и контрметрика к цели (поправка β, то есть больше выборки), список диагностических. Поправку выводим из правила запуска, а не из числа метрик в отчёте.
3. **Диагностические метрики и незапланированные сегменты решений не принимают.** Их находки — гипотезы для следующего теста.
4. **Сегменты — только заранее перечисленные и по признакам до назначения.** Доля сегмента в группах проверена, различие эффектов проверяем через взаимодействие, а не через «значим здесь, не значим там».
5. **Решение — одно из трёх, с записанной причиной.** Внедряем: успех значим, все guardrail прошли. Внедряем с условием: guardrail не определился — с порогом отката, holdout и сроком перепроверки. Не внедряем: ухудшение значимо или успех не значим. Слишком хороший результат сначала проверяем на ошибку.
